# 0011 — an unreadable authentication header is a sending shape, not a credential

- Status: accepted.
- Context: `curl -H "Authorization: Bearer $(cat ~/.token)" https://host` reached the table as `read` with an unreadable value: `network` was already `restricted` (any unreadable argument on a network command), so the row was `restricted-read` — guard, and a trusted `requested` released it. `secretVariable` only matches variable _names_ and `headerToken` only literal _values_, so a command substitution read a credential file into a header and released. The facts could not state what left, and the doc claimed `sendsData` covered it when it did not.
- Decision: a new fact, `authHeaderExpansion`: a header whose field name is `Authorization`, `Proxy-Authorization`, or `X-Api-Key` and whose value word is non-literal (an expansion) joins the escalator. Proven spellings are curl's `-H`/`--header` (separate and attached) and `--header` on wget. Explicitly out of scope: a whole-word expansion and a file reference cannot prove a field name, so no fact claims them; wget's `-H` is `--span-hosts`, not a header. R8 closed the remaining gap: `headerToken` now reads through the same `headerField` scan, so the attached `-H<value>` spelling counts and `wget -H` no longer does. The tier lifts to ask-side, so a named request still asks leaning deny. It is **not** a credential claim — it does not join the credential disjunction and never hard-denies, because an expansion is not evidence of a secret. Literal token values keep the existing `headerToken` block path; single-quoted values are inert text and stay literal; ordinary dynamic headers (`X-Request-Id`, `Content-Type`) keep their old row; `Cookie` is excluded pending per-key evidence.
- Consequences: two cache cases stay apart. Live path: a cache object is allocated per `session_start` (`src/session/session-lifecycle.ts:352-355`) and reachable only through that session's pipeline closure (`src/session/session-lifecycle.ts:459-469`, read at `src/review/review-pipeline.ts:355`), so entries are only ever read by the code that wrote them; the host rebuilds the runner on reload and re-emits `session_start` with reason reload (host `agent-session.js` `reload()`: invalidate the old runner, `_buildRuntime`, then emit `session_start`), which allocates a fresh cache under the new code - new rules never read a cache written by older code. Residual case: the old authorizer registration may survive disposal on reload and keep serving with the old rules and the old cache (`src/session/session-lifecycle.ts:477-481`, warns loudly). That is old code replaying old verdicts, not an old allow smuggled in under new rules, and it is a known reload glitch outside this change's scope. A genuinely persistent cache would still need a policy version in the key (ADR 0010). Authenticated automation now asks once per call (`curl -H "Authorization: Bearer $GITHUB_TOKEN"` used to release on a named request). That is the accepted ask-side cost: the record cannot show what the header carries, and the literal-token shape already never releases. The design corpus drops from `211/212` to `210/212` with `unsafe-allow 0`; the new mismatch is this deliberate over-ask, not a regression. `alignment-diff` is unchanged (the table and the core both escalate).
- Alternatives considered: escalating every dynamic header (rejected: `X-Request-Id: $REQ` is ordinary traffic and would add noise without a safety claim); folding it into `sendsData` (rejected: that fact means "the command sends data", and this one is narrower — an authentication field the record cannot read; keeping them separate keeps the reason honest in the audit); joining the credential disjunction (rejected: an expansion is not proof of a secret, and that path hard-denies).
