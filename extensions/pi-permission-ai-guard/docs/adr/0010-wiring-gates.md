# 0010 — wiring both lanes to one core: the conditions that must hold

- Status: accepted. Constrains the wiring; it does not authorize it.
- Context: the two lanes answer different questions today. The chat lane emits a verdict; the classifier lane answers four axes that a 15-row table turns into one. A shared core (`src/review/policy/`) reproduces the classifier table offline on ideal labels — agreement everywhere but the deliberate `unproven` movements (`decisions.md` holds the counts) — and is deliberately unwired. Wiring is the largest behaviour change in the project: a wrong release reaches the user as an allow.
- Decision: one policy core, two independent evidence adapters. Only code facts release; model claims tighten. Before any wiring lands, all of the following hold, and none of them is implied by a green offline number:
  1. **One authorization, one scope.** The prompt rewrite, both adapters, the fetch-then-execute fact, and the cache-version migration are authorized together, with the rollback stated. Gate-by-gate wiring is rejected: it leaves one lane on the old table with no single revert point.
  2. **A decision change moves the cache version.** A cached verdict from the old table must not be served after the wiring, and the cache key must carry the policy version that decided it.
  3. **`reason` crosses the same redaction boundary as the live lane.** `normalizeReason` redacts the chat lane's live reason; a claims-based reason must pass the same `normalizeAndRedactText` before it can ride the audit or notify path. This is a pre-wiring gate, not a follow-up.
  4. **The facts must be complete for the shapes the core rates.** A fetch-then-execute chain defers on both lanes; an anchor comes from the stripped transcript, never from the model; a non-bash ask (null command facts) defers neutrally; and a chat reply that omits an applicable concept cannot release. Each has a test through the real chain, not a hand-built input.
  5. **Adoption is gated by a freshly frozen set**, authored independently of the table and frozen before the prompt changes. A contaminated set is never reused, and a diagnostic set (one measuring coverage, not novelty) proves nothing about adoption.
  6. **Ideal-label alignment is a design check, not acceptance.** `alignment-diff` compares the core to the table on ideal labels and proves `kind`/`lean` only; acceptance is the unit tests above plus a pre-registered paid round with its own ceiling.
- Consequences: the C1 execution plan is deleted; its conditions live here. `src/review/policy/` stays additive and unwired until an L3 says otherwise, and nothing in this ADR is approval to run a paid round.
- Alternatives considered: gate-by-gate authorization (rejected: no single rollback, and a half-wired tree has no coherent baseline to measure); keeping the plan as the record (rejected: process outlives its document, while these constraints must outlive it).
