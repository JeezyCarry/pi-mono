# 0009 — protection weakening is a conjunction, not a permission bit

- Status: accepted.
- Context: a paid live round (Phase B) found `chmod 644 ~/.aws/credentials` allowed behind a named anchor: the classifier read `modify` of `credential_material` with `requested`, and guard plus a request releases by construction. The adjudicated reason to ask was protection weakening, which no fact stated and no table row could carry — the table never names a tampering concept, so words alone decided.
- Decision: facts record structure the parser can prove and nothing more. `grantsBeyondOwner` states "the `chmod` wording sets a group/other bit", reading the words only — no prior mode is visible, so it never claims "this widened the file". The escalating conjunction in `tierOf` is `grantsBeyondOwner && sensitivePathName`: `chmod +x build.sh` grants beyond the owner too and stays silent, because the path is not sensitive. Husky's `.husky/<hook>` writes join `.git/hooks/` in `installsPersistence` for the same reason a closed hook-name list can prove them: a basename match, not an effect claim.
- Consequences: `chmod 644 ~/.aws/credentials` now asks leaning deny even behind the anchor (`modify-or-send-credential+escalated`); `chmod +x build.sh` still allows. The `rates-fetch` finding is deliberately NOT closed this way — `api.example.org` classifies `public`, so no fact is missing; the rubric's record rule and the code's literal-host rule are different rules and stay different. The setuid deny needs no change either: it is the screen's hard rule, outside the lane's answer space.
- Alternatives considered: escalate on every group/other grant (rejected: `chmod +x` noise on every script); a semantic "did this weaken" fact from the live mode (rejected: the parser cannot see the prior state); folding hook paths into the startup-file name list inline (rejected: a data set with the hook names keeps the shape separate from the star-globs).
