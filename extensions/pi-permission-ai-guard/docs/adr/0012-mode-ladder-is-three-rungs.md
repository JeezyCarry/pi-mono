# 0012 — the mode ladder is three built-in rungs plus a custom row

- Status: accepted. Supersedes ADR 0002's mode set (the lean-routing decision itself still holds); the mode names in ADR 0002's body are historical.
- Follow-up (same change, second slice): `mode: "custom"` runs the operator-defined `customMode` block — two cut lines (`allowThrough`, `denyFrom`) plus the reviewer-failure lane (`onReviewFailure: deny|defer`), and nothing else. A mode is two boundaries, so a custom row is contiguous by construction; there are no per-rung cells to set incoherently. `mode: "custom"` with no block repairs to `default` with a config issue (a mode choice never takes the guard offline); a configured custom joins the picker and the casual cycle last, renders red exactly when it never asks, and a pair redrawing a built-in rung is reported as redundant. The failure lane is `deny|defer` by schema — never `allow`, whatever the cuts say.
- Context: the ladder shipped four rungs. `lenient` differed from `auto` on exactly one rung — a benign-leaned doubt passed instead of asking — while still asking on neutral doubts and on every soft deny, so the middle of the ladder needed two sentences to explain and neither sentence predicted an operator's actual experience. `permissive` had the opposite problem: in every peer product the word means "no protection at all" (Claude Code's `bypassPermissions`, Codex's `--yolo`, Gemini CLI's `yolo`, Cursor's "Run Everything", Cline's YOLO), while this rung blocks every deny and every danger-leaned doubt and never prompts. The name promised the opposite of the behaviour, and "auto-approved" copy in notices made the collision worse by implying the mode approves what the reviewer denied.
- Decision: three built-in rungs, `strict` → `default` → `auto`, each still two cut lines on `SUSPICION_ORDER`. The surviving rows keep their cuts and reviewer-failure lanes unchanged (`strict` allow through `allow` / deny from `defer-benign`, machinery denies; `default` allow through `allow` / deny from `hard-deny`, machinery defers; `auto` allow through `defer-neutral` / deny from `defer-danger`, machinery denies). `permissive` is renamed `auto` with identical behaviour: it is the ask-free rung, so the lean decides between allow and deny there, a danger-leaned doubt blocks rather than auto-flowing into an allow, and every deny blocks. `lenient` is removed; a configuration that names it falls back to `default` and reports a migration notice saying which rung disappeared and that the benign-lean pass-through is the part a future user-defined mode would express. A retired `mode` value is rewritten in place before validation (`permissive` → `auto` with no behaviour change, `lenient` → `default`), so the operator sees a named migration instead of the enum's generic rejection; session overrides carrying a retired value are dropped as unknown and the session starts from the configured mode. The footer's warning-red emphasis is derived from the table (the cycled rung with no ask band) rather than hand-set, so it cannot drift from the mode it marks. Operator copy says "allowed without asking" and "this mode allows the request without asking" instead of "auto-approved", because "auto" is now a mode name and automatic approval is a different thing. Documentation names the peer products whose yolo modes differ from `auto` rather than calling it "not yolo" in the abstract.
- Consequences: `default` still asks on every soft deny and every unresolved doubt, so the ladder keeps an ask path for an undecided verdict; `auto` behaves exactly as `permissive` did, so no operator's existing posture changes except the name in their config and the notice they see once. The `lenient` rung's ask-on-neutral behaviour is gone with it — an operator who relied on it loses a rung rather than gaining a different one, which is the accepted cost of a ladder that can be explained in one sentence per rung. The design corpus loses its `lenient` column and `paper-validate` replays three modes instead of four; the headline is unchanged (210/212, `unsafe-allow` 0) because no case's intent depended on that rung, and `alignment-diff` is unchanged (186/212 agree, 26 intended movements, 0 other differences). Retired values keep loading, so an upgrade never turns a saved config into a load failure — the one place the project accepts a migration shim is a value rename that would otherwise brick an operator's config at startup.
- Alternatives considered: keeping `lenient` (rejected: its only distinguishing rung duplicates `auto`, and it costs a second sentence per explanation; the exact middle it offers — benign-leaned passes, neutral and danger ask, soft denials ask — becomes expressible as a user-defined two-cut-line mode, which is the planned extension, not a reason to keep a built-in rung); keeping the name `permissive` (rejected: it means "no protection" in every peer product while this rung blocks every deny and every danger-leaned doubt, and the misreading is dangerous in the direction that matters); `unattended` (rejected: it names the scene — no human present — not the permission policy, and the two come apart in headless runs with `default`); `dontAsk` (rejected: inverted polarity, it names the prompt rather than the cut lines, and Claude Code's own `dontAsk` bundles deny rules this rung does not have); `autopilot` (rejected: it promises autonomous completion of the task, which the guard does not do); collapsing to `strict`/`default` (rejected: ask-free automation is what operators run for batch work, and removing it pushes them to the engine's yolo, which has no backstop at all); adding a built-in yolo rung (rejected: the guard's product is a backstop, yolo is the engine's own flag, and a mode that neither asks nor blocks would make the reviewer pointless); a user-defined mode in this change (done as the follow-up slice above, with its own schema, resolver, and fallback contract).
